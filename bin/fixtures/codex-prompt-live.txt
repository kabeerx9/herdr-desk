• I favor a dedicated Mumbai VPS, but the latency diagnosis is still a hypothesis. Measure first-request-after-idle and warm-request p50/p95, separating DB connection, queries and auth time. p50 alone
  will hide the complaint. Fluid compute supports Python and can reduce cold starts; test its current configuration before moving. Warm-up pings aren’t an availability guarantee. Persistent
  connections to a transaction pooler can save connection setup—the pooler does not inherently require reconnecting every request.

  The plan needs these corrections:

  • Pricing/location: Lightsail’s IPv4 1 GB plan is $7/month, not $5. DigitalOcean’s 1 GB plan is $6/month in Bangalore, not Mumbai.

  • Commercial hosting: moving only the API leaves the SPA on Hobby, which is restricted to personal, non-commercial use. Address both when commercial.

  • Connections: settings already use CONN_MAX_AGE=60 and health checks outside transaction mode. Session pooling is reasonable; budget connections across workers and deploy overlap.

  • Memory/deployment: two workers on 1 GB need measured RSS and burst testing. Build images in CI; deploy immutable tags with serialized migrations, readiness checks and previous-image rollback. Boot
    migrations couple every restart to schema changes; code rollback cannot undo them.

  • Operations: accept single-instance downtime explicitly. Add uptime/OOM/disk alerts, log rotation, patching, cron failure alerts and shared throttling if enforcement matters.

  • Backups: nightly dumps imply up to 24 hours’ loss. Encrypt, expire, alert and test restoration. Supabase pausing and AWS account expiry remain unresolved.

  I’d keep Django/Compose/Caddy and choose Lightsail Mumbai. Railway’s Singapore region adds a cross-region DB path. Avoid the nearly full Hermes host. No stack rewrite needed.
